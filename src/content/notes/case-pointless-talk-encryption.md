## 질문

서버 보관 데이터를 줄이는 메신저는 서버가 내용을 읽지 못하는 메신저와 같은가?

## 출발점

「Pointless Talk 분석」 대화에는 Pointless.chat의 메신저 베타에 대해 전송 중 암호화는 있지만 E2EE 구현은 어렵다는 설명이 전달되었다. 기술·사용성·브랜딩을 함께 평가하려던 질문에서 보호 범위를 따로 읽을 필요가 생겼다.

과거 공유 이미지의 원본과 전체 개발자 발언은 이번 작업에서 다시 열람하지 못했다. 그 발언을 직접 인용하거나 내부 구현의 근거로 쓰지 않고 현재 공식 자료로 보완한다.

## 현재 공식 설명에서 확인한 사례

2026-10-03에 한국어 [신뢰 페이지](https://talk.pointless.chat/trust?lang=ko) 본문을 확인했다.

- 기기와 서버 사이 통신은 HTTPS를 사용한다고 설명한다.
- E2EE를 제공하지 않으며 서버 시스템이 전달을 위해 내용을 처리할 수 있다고 명시한다.
- 메시지·첨부의 서버 보관은 최대 72시간이며 기기 저장 확인 후 임시 사본을 정리한다는 정책이다.
- 친구 관계·그룹·로그인·전달·읽음 정보는 본문과 다른 기간 보관될 수 있다.

**공식 설명 확인:** 보관 정책의 실제 실행, 백업 삭제, 서버 권한이나 암호화 코드를 감사한 것은 아니다. 이 노트의 보호 범위는 해당 날짜의 설명에 근거한다.

## 비교

| 보호 방식 | 줄이려는 위험 | 이 방식만으로 보장하지 않는 것 |
| --- | --- | --- |
| HTTPS/TLS | 기기와 서버 사이 전송의 도청·변조 | 서버의 본문 접근 불가능 |
| 보관 최소화 | 오래 남는 서버 사본의 위험 | 전달 중 본문 접근 불가능 |
| 대화 접근 제어 | 권한 없는 사용자의 접근 | 운영 시스템 자체의 접근 불가능 |
| E2EE | 중간 서버가 본문을 해독하는 위험 | 침해된 기기·수신자의 저장 통제 |

TLS의 범위는 [MDN](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Transport_Layer_Security)과 대조했다. Mastodon도 [private mention 안내](https://docs.joinmastodon.org/user/posting/)에서 서버 DB 관리자의 본문 접근 가능성을 알린다. “비공개”와 “서버도 읽을 수 없음”은 같은 보장이 아니다.

## 내가 여기서 배운 것 / 수정한 개념

“E2EE가 없으니 아무 보호도 없다”와 “암호화하니 서버도 못 본다”는 둘 다 구간을 지운 설명이다. [암호화는 어느 구간을 보호하는가](/notes/encryption-protection-boundary/)를 **전송·내용 접근·보관·단말**의 별도 질문으로 바꾼 사례다.

브랜딩 평가에서도 데이터 최소화라는 실제 약속과 E2EE라는 다른 약속을 섞지 않아야 한다.

## 다시 사용할 수 있는 질문

- 공식 설명에서 E2EE를 명시적으로 구분하는가?
- 서버가 전달할 때 접근 가능한 본문과 메타데이터는 무엇인가?
- 72시간 같은 기간은 본문·첨부·로그·백업 모두에 적용되는가?
- 권한 확인·삭제·복구 정책의 구현 증거는 어디에 있는가?
- 서비스 설명과 사용자가 기대하는 비밀성 사이에 차이가 있는가?

## 한계 / 반례

공식 정책은 독립 감사가 아니다. 향후 E2EE나 보관 방식이 바뀌면 다시 확인해야 한다. E2EE 유무 하나로 서비스의 전체 사용 가치나 안전 수준을 단정하지 않는다.
