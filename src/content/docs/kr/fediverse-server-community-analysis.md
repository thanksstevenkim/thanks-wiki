## 이 문서는 무엇을 위한 것인가

이 문서는 새로운 Fediverse 서버를 처음 보거나, 이미 운영 중인 서버의 가입·정착·운영 문제를 살필 때 쓰는 분석 가이드다. 소프트웨어 기능표만 비교하거나 “분산되어 있으니 자유롭다”는 결론에서 멈추지 않고, **가입 전 선택부터 떠날 때의 비용까지 한 흐름으로 확인하는 것**을 목표로 한다.

Fediverse 전체를 하나의 서비스처럼 평가하지 않는다. Mastodon·Misskey 같은 소프트웨어, 개별 서버의 정책, 그 안에서 형성된 커뮤니티는 서로 연결되어 있지만 같은 대상은 아니다.

## 핵심 구분

| 구분 | 먼저 확인할 것 | 이것만으로 알 수 없는 것 |
| --- | --- | --- |
| 소프트웨어 | 게시·발견·반응·이동 기능 | 개별 서버의 규칙과 실제 운영 |
| 서버(instance) | 가입 방식·운영 주체·연합 제한 | 이용자 사이에 형성된 관습 |
| 가입 상태 | 등록·이메일 인증·관리자 승인 | 계속 사용할 이유를 찾았는지 |
| 상호작용 | 팔로우·게시·답장·알림 | 그 경험이 당사자에게 의미 있었는지 |
| 거버넌스 | 규칙·신고 창구·조치 범위 | 모든 판단이 일관되거나 오류가 없는지 |
| 이동 가능성 | 자동 이동·수동 내보내기·이동 불가 항목 | 실제로 관계와 기록을 다시 만들 비용 |

이 구분은 각각을 따로 떼어 보려는 것이 아니다. 어느 단계에서 생긴 문제를 다른 단계의 성공으로 덮지 않기 위한 것이다.

## 분석 순서

### 1. 지금 무엇을 고르는지 정한다

먼저 선택 대상을 한 문장으로 적는다.

- 소프트웨어의 기능과 표현 방식을 고르는가?
- 특정 서버의 운영 정책과 가입 방식을 고르는가?
- 이미 아는 사람이 있는 커뮤니티를 고르는가?
- 기존 계정에서 떠날 대상을 찾는가?

예를 들어 “Mastodon을 쓴다”는 말만으로는 어느 서버의 규칙을 따르는지 알 수 없다. 반대로 서버 정책만 읽어서는 다른 소프트웨어와 상호작용할 때 기능이 어떻게 표현되는지 알 수 없다.

### 2. 가입 가능성과 실제 진입을 나눈다

가입 버튼이 있다는 사실과 커뮤니티에 들어왔다는 경험을 구분한다.

1. 계정 등록
2. 이메일 인증
3. 관리자 승인
4. 로그인
5. 관심 계정이나 글 발견
6. 첫 팔로우·게시·답장·알림
7. 당사자가 의미 있다고 느낀 첫 상호작용

각 단계에는 **확인한 상태**, **다음 행동을 알려 주는 안내**, **멈춘 이유에 대한 증거**를 따로 기록한다. 데이터베이스의 대기 상태만으로 사람의 의도나 이탈 이유를 추정하지 않는다. 조용히 읽는 이용자에게는 답장보다 원하는 글을 계속 발견하는 일이 더 의미 있을 수도 있다.

### 3. 첫 관계가 생기는 경로를 본다

승인 이후 다음 경로가 실제로 보이는지 확인한다.

- 관심사·언어에 맞는 계정이나 해시태그를 찾을 수 있는가?
- 로컬·연합 타임라인이 초보자에게 무엇인지 설명되는가?
- 질문하거나 도움을 요청할 창구가 있는가?
- 첫 게시물이나 자기소개를 강요하지 않으면서 참여 방법을 안내하는가?
- 읽기만 하는 이용자를 실패로 분류하지 않는가?

팔로우 수나 첫 답장까지의 시간을 바로 정착 지표로 확정하지 않는다. 무엇이 의미 있는 경험인지 먼저 정의하고, 측정할 경우 목적·동의·보관 범위를 정한다.

### 4. 서버를 거버넌스 단위로 읽는다

규칙 문구보다 규칙이 작동하는 경로를 함께 본다.

- 규칙은 허용·제한하는 행동을 이해할 수 있게 쓰였는가?
- 신고나 문의를 누가, 어떤 창구에서 받는가?
- 운영자가 필요할 때 응답 가능한 존재로 보이는가?
- 조치의 목적과 범위를 설명할 수 있는가?
- 다른 서버와의 연합을 제한하는 기준이 있는가?
- 오탐이나 판단 오류를 다룰 이의 제기 경로가 있는가?

운영의 가시성은 모든 신고 내용과 판단을 공개한다는 뜻이 아니다. 사생활을 보호하면서도 규칙의 취지, 연락 가능한 창구, 조치가 미칠 범위는 설명할 수 있다.

### 5. 연합 경계를 실제 경험으로 확인한다

연합되어 있다는 말은 모든 기능과 관계가 동일하게 보인다는 뜻이 아니다.

- 원격 팔로우·답장·검색이 어느 범위에서 작동하는가?
- 리액션·인용·공개 범위 같은 표현이 상대 소프트웨어에서 어떻게 바뀌는가?
- 서버 단위 제한이 어떤 연결에 영향을 주는가?
- 기능 차이인지, 개별 서버 정책인지, 클라이언트 차이인지 구분했는가?

기능 문서는 가능한 동작을 알려 준다. 실제 서버·fork·버전·클라이언트 조합의 결과는 필요한 범위에서 별도로 확인한다.

### 6. 이동 권리와 이동 비용을 함께 적는다

“떠날 수 있다”는 설명 다음에 무엇을 가져갈 수 있는지 적는다.

| 항목 | 확인할 질문 |
| --- | --- |
| 계정 주소 | 새 주소를 관계망에 어떻게 알리는가? |
| 팔로워 | 자동 이동을 상대 서버가 지원하는가? |
| 팔로우·차단·음소거 | 별도 내보내기·가져오기가 필요한가? |
| 게시물·미디어 | 보관용 아카이브와 새 서버로의 가져오기를 구분했는가? |
| 서버 문화 | 새 규칙과 관습을 다시 익힐 비용은 무엇인가? |
| 관계 | 이전 기능이 옮기지 못하는 신뢰와 맥락은 무엇인가? |

Mastodon의 공식 이동 안내처럼 자동으로 이어지는 항목, 사용자가 별도로 옮기는 항목, 새 서버로 가져올 수 없는 항목을 나눠 적는다. 그 범위를 다른 ActivityPub 소프트웨어 전체의 보장으로 확대하지 않는다.

### 7. 사실·해석·다음 확인을 분리한다

관찰을 다음 세 칸으로 남기면 서버에 대한 인상과 확인된 동작이 섞이는 일을 줄일 수 있다.

| 확인한 사실 | 현재 해석 | 다음에 확인할 것 |
| --- | --- | --- |
| 어떤 단계·화면·문서·로그를 확인했는가? | 무엇이 문제이거나 장점이라고 보는가? | 다른 설명을 가를 자료는 무엇인가? |

문서에 적힌 정책, 로그에 남은 상태, 이용자의 경험담은 서로 다른 범위의 증거다. 하나로 다른 하나를 대신하지 않는다.

## 사례

### 가입 검토 봇: 정상 대기와 장애를 나누기

가입 webhook과 HTTP 200이 확인됐는데 Matrix 검토 카드가 나타나지 않은 사건이 있었다. 공개 런북에는 봇이 이메일 인증을 기다린 뒤 카드를 게시하는 흐름이 기록되어 있었다. 따라서 카드가 없다는 화면만으로 전체 실패를 판정하지 않고, **webhook 수신 → 인증 대기 → 승인 상태 → 카드 게시**를 나눠 진단해야 했다.

이 사건은 모든 누락 카드의 원인이 이메일 미인증이었다는 증거가 아니다. 당시 확보하지 못한 계정 상태와 전체 로그는 미확인으로 남는다.

→ 자세한 사건 기록: [가입 검토 봇: 이메일 인증 대기를 장애로 읽었다](/notes/case-signup-bot-email-wait/)

### Mastodon·Misskey: 연결성과 같은 경험을 구분하기

Mastodon의 계정 이동에서는 지원되는 팔로워 이동, 별도의 CSV 가져오기, 새 서버로 가져오지 못하는 게시물·미디어를 구분해야 한다. Misskey 리액션도 다른 서버에서 대체로 Like로 전달될 수 있으므로 연결되어 있다는 사실만으로 표현이 동일하다고 볼 수 없다.

→ 자세한 비교: [Mastodon·Misskey: 연결되어도 경험은 같지 않다](/notes/case-mastodon-misskey-choice/)

### 가입 완료와 관계 발견 사이

계정 등록, 이메일 인증, 관리자 승인은 각각 확인 가능한 상태다. 그러나 관심 계정 발견이나 만족스러운 대화는 그 상태에서 자동으로 따라오지 않는다. 가입 흐름을 개선할 때에는 기술적 완료 이후에 사용자가 선택할 수 있는 발견·도움 경로를 별도로 살핀다.

→ 자세한 분석: [Mastodon: 가입 완료와 관계 발견 사이의 단계](/notes/case-mastodon-onboarding/)

## 흔히 생기는 오류

- Mastodon이라는 소프트웨어와 특정 Mastodon 서버의 정책을 같은 것으로 설명한다.
- 계정 생성 수를 인증·승인·정착까지 완료한 이용자 수로 읽는다.
- 관리 화면의 상태만 보고 사용자가 멈춘 이유를 추정한다.
- 규칙이 게시되어 있다는 사실을 일관된 집행의 증거로 삼는다.
- 연합되어 있으면 기능과 표현도 그대로 전달된다고 가정한다.
- 계정 이동 기능이 관계·게시물·서버 문화까지 모두 옮긴다고 말한다.
- 첫 답장이나 활발한 게시만 성공으로 보고 조용한 이용 방식을 지운다.

## 다시 사용할 질문

- 나는 소프트웨어, 서버, 커뮤니티 중 무엇을 고르고 있는가?
- 가입 이후 지금 확인한 단계는 등록·인증·승인·로그인 중 어디인가?
- 사용자는 다음 행동과 대기 이유를 알 수 있는가?
- 관심사와 언어에 맞는 관계를 스스로 찾을 경로가 있는가?
- 규칙·신고 창구·운영 주체·연합 제한을 확인할 수 있는가?
- 운영 정책이 실제 응답과 조치에서 어떻게 드러나는가?
- 원격 서버에서 기능과 표현이 같은 의미로 전달되는가?
- 떠날 때 자동으로 이동되는 것, 직접 옮길 것, 남겨야 할 것은 무엇인가?
- 지금의 결론은 문서, 로그, 직접 관찰, 이용자 경험 중 무엇에 근거하는가?
- 이 해석을 뒤집을 수 있는 반례나 다음 확인은 무엇인가?
