## 이 문서가 답하려는 질문

서비스나 자동화가 “안 된다”고 보일 때, **마지막으로 성공이 확인된 단계와 아직 확인되지 않은 다음 단계**를 어떻게 나눠서 조사할까? 이 문서는 [장애 기록이 대응 절차가 되는 순간](/notes/incident-to-runbook/)에 모인 네 사건을 재사용 가능한 진단 순서로 압축한다. 특정 설정값이나 명령을 모든 환경에 적용하는 복구 지침은 아니다.

사례는 공개 운영 기록을 재구성한 Notes에 근거한다. 원본 로그·설정 diff·최종 테스트 출력이 빠진 부분은 각 Case의 미확인 범위를 따른다. 아래 순서는 당시 운영자가 실제로 밟은 순서를 복원한 것이 아니라 **다음 사건에서 사용할 분석 절차**다.

## 사례에서 반복된 질문

| 사례와 증상 | 마지막으로 확인된 것 | 그 사실만으로 보장되지 않는 것 | 다음에 가를 경계 |
| --- | --- | --- | --- |
| [Cloudflare 521](/notes/case-cloudflare-521-nginx/) | 앱 컨테이너·Puma·DB의 정상 상태 | 외부 요청을 받는 Nginx의 기동과 웹 접근 | 프록시 구성 검사·서비스 상태·경유 접속 |
| [Sidekiq의 Elasticsearch 연결 실패](/notes/case-elasticsearch-service-name/) | Elasticsearch 실행 상태 | Sidekiq가 설정한 이름의 해석과 연결 | Compose 이름·별칭과 주입된 `ES_HOST` |
| [가입 검토 카드 부재](/notes/case-signup-bot-email-wait/) | `account.created` 수신·POST 200·polling 시작 | 이메일 인증·승인·Matrix 카드 게시 | `confirmed`와 `approved`, 대기 설정, 게시 기록 |
| [Mastodon fork CI 실패](/notes/case-mastodon-fork-ci/) | 운영 서비스와 별개로 보고된 CI 실패; 원 기록상 깨끗한 upstream lint 통과 | fork의 코드·설정·전체 CI 통과 | 같은 릴리스의 fork 차이와 실패 검사별 재검증 |

앞의 세 사례는 요청이나 처리 흐름의 **단계 사이**를 가른다. CI 사례는 성공한 기준 환경과 실패한 fork의 **차이**를 가른다. 동일한 원인이 반복됐다는 뜻은 아니다.

## 먼저 구분할 변수

| 변수 | 적을 내용 |
| --- | --- |
| 영향 범위 | 외부 접속, 검색, 검토 카드, CI 중 실제로 실패한 기능과 운영 영향 |
| 경로 또는 대조군 | 요청이 지나는 구성 요소와 상태 전이, 또는 같은 릴리스·명령의 기준 환경 |
| 증거의 강도 | 화면의 부재, 상태값, HTTP 응답, 서비스 로그, 작업 완료 중 무엇을 확보했는가 |
| 변경 범위 | 직전 업그레이드·설정·서비스명·fork 변경 중 확인한 차이 |
| 완료 기준 | 프로세스 실행, 연결, 사용자 작업, 전체 테스트 중 어디까지 다시 확인할 것인가 |

HTTP 200, `healthy`, “서비스 실행 중”은 각각 **해당 경계의 증거**다. 전체 작업의 완료 표시로 승격하지 않는다. 반대로 화면에 결과가 없다는 사실만으로 내부의 모든 단계가 실패했다고 판정하지 않는다.

## 실제 분석 순서

### 1. 증상과 영향을 한 문장씩 적는다

사용자에게 보인 결과와 실제로 확인된 영향 범위를 분리한다. “웹 접속 불가”와 “모든 컨테이너 중단”, “검색 불가”와 “Elasticsearch 데이터 손상”, “CI 실패”와 “운영 서비스 장애”는 각각 다른 주장이다. 아직 확인하지 못한 영향은 미확인으로 남긴다.

### 2. 경로를 단계별로 그린다

요청·작업이 지나야 하는 구성 요소와 각 단계의 완료 조건을 적는다. 예를 들어 가입 검토 흐름은 webhook 수신 → 계정 상태 polling → 이메일 인증 대기 → 카드 게시 → 관리자 조치처럼 나눌 수 있다. 실제 배포에 없는 단계는 넣지 않는다. CI라면 실패 명령과 대상 파일, 같은 태그의 upstream을 대조할 수 있는지 적는다.

### 3. 마지막 성공과 첫 미확인을 표시한다

각 로그나 상태가 **무엇을 증명하며 무엇을 증명하지 않는지** 한 줄씩 적는다. Cloudflare 521 사례에서 앱 상태는 Nginx 기동을 대신하지 않았다. 가입 봇 사례에서 POST 200은 카드 게시를 대신하지 않았다. 증거가 없다면 “첫 실패”라고 확정하지 않고 “첫 미확인”이라고 쓴다.

### 4. 서로 다른 설명을 가를 확인을 고른다

현재 관찰과 맞는 가설을 두세 개로 좁히고, 각각을 구분할 값이나 로그를 정한다. Nginx라면 구성 검사와 서비스 상태, 이름 해석 오류라면 실제 서비스명·네트워크·주입된 환경변수, 카드 부재라면 인증·승인 상태와 대기 시간, CI라면 동일 조건의 upstream과 fork diff다. 이는 사례에서 추린 **확인 항목**이지 모든 사건에 일괄 실행한 명령 목록이 아니다.

정상 대기와 오류도 구분한다. 봇이 인증을 기다리도록 설정돼 있다면 카드 부재는 해당 단계에서 예상 가능한 상태다. 다만 당시 모든 계정의 상태를 확인한 자료가 없으므로 모든 누락을 인증 대기로 설명하지 않는다.

### 5. 변경은 확인된 차이에 한정한다

설정값을 복사하기 전에 현재 배포의 서비스명·별칭·환경변수를 확인한다. CI 기대값을 고치기 전에 변경 의도와 upstream 차이를 설명한다. 원 사건에서는 Nginx 중복 구성을 제거했고, 다른 사건에서는 그 배포의 `ES_HOST`를 `elasticsearch`에서 `es`로 맞췄다. 이 값이나 조치가 다른 배포의 정답은 아니다.

### 6. 원래 실패한 일을 다시 확인한다

서비스가 기동하는 것과 외부 웹 화면이 열리는 것, Elasticsearch 연결과 검색 기능, webhook 수신과 검토 카드·최종 승인, lint 통과와 전체 CI 통과를 각각 나눠 기록한다. [fork CI 사례](/notes/case-mastodon-fork-ci/)의 공개 기록에는 수정 후 lint exit 0은 있지만 CSP·Tag RSpec의 최종 실행 출력은 없다. 그 결과를 “전체 CI 통과”로 채우지 않는다.

### 7. 사건 기록과 재사용 절차를 분리한다

Case에는 당시 환경, 증상, 확보한 로그, 수정, 실제 검증 범위와 빠진 증거를 남긴다. Docs에는 다른 환경에서도 **무엇을 먼저 구분할지**만 남긴다. 반례나 후속 증거가 나오면 Case의 역사적 기록을 지우기보다 현재 절차가 어디서 달라지는지 갱신한다.

## 잘못된 판단으로 이어지기 쉬운 지점

- 가장 눈에 띄는 오류 화면을 원인으로 확정한다. 521은 외부에서 관찰한 증상이며 이 사건의 원인은 Nginx 기동 실패였다.
- 실행 중인 구성 요소를 연결 성공의 증거로 쓴다. Elasticsearch가 떠 있어도 소비자가 다른 이름을 참조할 수 있다.
- 이벤트 수신을 업무 완료로 센다. 가입 webhook과 인증·게시·승인은 서로 다른 단계다.
- 결과가 늦게 보이는 상태를 장애로, 다른 사람의 대기를 의도적 이탈로 읽는다.
- upstream이 통과했다고 fork의 모든 기능이 틀렸다고 결론 내리거나, 일부 lint 통과를 전체 CI 통과로 쓴다.
- 복구 이후에 그 조치만이 원인이었다고 기록한다. 변경 전후의 증거와 남은 대안 설명을 적는다.

## 적용 한계와 반례

경계가 하나만 고장 난다는 보장은 없다. 프록시와 앱이 동시에 실패할 수도 있고, 인증 대기와 Matrix 전송 오류가 함께 있을 수도 있다. 처음 찾은 원인을 해결한 뒤 **원래 실패한 사용자 작업**을 다시 확인해야 하는 이유다.

로그가 없는 단계는 실제 실패 위치를 알 수 없다. 원 사건의 로그가 축약됐거나 테스트 결과가 빠졌다면 그 범위를 넘어서 회고하지 않는다. 새 환경의 버전·설정·연결 방식이 다르면 사례의 조치보다 현재의 경계 확인을 우선한다. 이 절차는 원인 분석의 순서이지 가용성이나 보안을 보장하는 검사표가 아니다.

## 다음 사건에서 바로 사용할 기록 양식

1. **증상 / 영향:** 누가 무엇을 못 했으며, 확인하지 못한 영향은 무엇인가?
2. **경로 / 대조군:** 요청의 단계 또는 같은 조건의 기준 환경은 무엇인가?
3. **마지막 성공:** 어느 로그·상태·동작을 실제로 확인했는가?
4. **첫 미확인:** 그 증거가 보장하지 않는 바로 다음 단계는 무엇인가?
5. **구분할 가설:** 서로 다른 원인을 가를 가장 작은 확인은 무엇인가?
6. **변경 / 이유:** 무엇을 어떤 증거에 따라 바꿨는가?
7. **검증 / 한계:** 원래 실패한 작업은 어디까지 회복됐고, 최종 출력이 없는 검사는 무엇인가?
