새 서버를 고르거나 운영 상태를 평가할 때는 기능 목록 하나보다 **가입에서 관계를 맺고, 문제에 대응하고, 떠나는 과정**을 순서대로 본다. [분산화와 선택 비용](/notes/decentralization-not-freedom/), [서버의 규칙](/notes/server-as-governed-place/), [운영의 가시성](/notes/operator-invisible-community/), [첫 관계](/notes/first-meaningful-interaction/)에서 반복된 질문을 실제 점검 순서로 모았다. 이 문서는 특정 서버의 품질 인증이나 정착률 분석이 아니다.

## 1. 소프트웨어, 서버, 클라이언트를 적는다

Mastodon·Misskey 같은 소프트웨어와 개별 인스턴스의 가입 방식·규칙·운영자는 구분한다. 클라이언트에서 보이는 기능도 원격 서버에 같은 형태로 전달되는지 확인한다. [Mastodon·Misskey 사례](/notes/case-mastodon-misskey-choice/)에는 리액션 표현과 계정 이동에서 이 차이가 남는 범위를 적었다. 연결된 네트워크라는 사실만으로 동일한 이용 경험을 보장하지 않는다.

## 2. 가입을 상태별로 따라간다

서버에 계정을 만들 수 있는지 확인한 다음, 계정 생성 → 이메일 인증 → 관리자 승인 → 로그인 → 첫 팔로우·게시·답장 → 계속 쓸 이유를 찾은 경험을 각각 따로 기록한다. 서버마다 승인 단계는 다를 수 있다. **첫 의미 있는 상호작용**은 정착을 물어볼 가설이지 모든 이용자가 답장을 해야 한다는 기준은 아니다. 읽기만 하는 이용자도 가치 있는 이용자일 수 있다.

| 관찰 | 확인 가능한 범위 | 다음 질문 |
| --- | --- | --- |
| `account.created`·HTTP 200 | 이벤트가 접수됨 | 인증이 끝났는가? |
| 이메일 인증 | 인증 상태 | 승인 대기인가? |
| 관리자 승인 | 계정 사용 허가 | 관심 계정을 찾을 길이 있는가? |
| 팔로우·답장 | 각각의 행동 | 사용자에게 의미가 있었는가? |

[가입 검토 봇 사례](/notes/case-signup-bot-email-wait/)는 webhook 수신과 검토 카드 게시 사이에 인증 대기가 있었던 기록이다. 모든 카드 부재의 원인을 인증으로 확정하지 않았으며, [가입 상태와 관계 발견의 사례](/notes/case-mastodon-onboarding/)는 승인 이후의 측정 결과가 없음을 명시한다. 문제가 보이면 **마지막으로 확인한 단계**부터 추적한다. 대기 이유를 가입자의 의도로 추정하지 않는다.

## 3. 규칙이 작동하는 경로를 본다

가입 화면의 규칙, 신고 창구, 응답 방식, 공개 공지, 다른 서버와의 연합 제한을 확인한다. 운영자가 모든 사건의 사적 내용을 공개할 수는 없다. 그래도 이용자가 규칙의 뜻과 문제 제기 경로, 조치가 미치는 범위를 알 수 있는가? [모더레이션의 경계](/notes/moderation-boundaries/)와 [운영자가 보이는 순간](/notes/operator-invisible-community/)이 이 질문을 나눈다.

규칙이 짧거나 길다는 사실만으로 좋은 운영을 판정하지 않는다. 공개 문구와 실제 대응을 비교할 사례가 없다면 판단을 보류한다. 서버 차단은 특정 계정만이 아니라 서버 사이의 연결에도 영향을 줄 수 있으므로 범위를 먼저 적는다.

## 4. 관계 발견을 확인한다

가입자가 언어·관심사에 맞는 계정이나 대화에 도달할 수 있는가? 추천과 안내가 사용자 선택을 도우면서도 관계를 강제하지 않는가? 첫 팔로우 수와 첫 답장 수를 정착의 같은 지표로 묶지 않는다. 이용자 조사나 분석을 한다면 동의와 필요한 최소 자료의 범위를 정한다. 현재 사례에는 첫 상호작용이 재방문을 높인다는 실험이 없다.

## 5. 떠날 때 무엇이 옮겨지는지 확인한다

새 서버의 규칙과 가입 가능 상태를 본 뒤 팔로워 이동, CSV로 다룰 목록, 과거 게시물·미디어를 각각 점검한다. Mastodon의 [공식 이동 안내](https://docs.joinmastodon.org/user/moving/)에서 다루는 이동 기능을 모든 ActivityPub 구현으로 확대하지 않는다. 계정을 옮길 수 있다는 선택권과 관계·기록·표현을 유지하는 비용을 함께 적는다.

### 새 서버에서 바로 물어볼 질문

- 내가 고르는 것은 소프트웨어, 운영자, 규칙, 클라이언트 중 무엇인가?
- 등록·인증·승인 중 어디까지 완료했는가? 막혔다면 다음 행동이 보이는가?
- 관심 있는 사람을 어떻게 발견하고, 조용히 읽을 수도 있는가?
- 규칙과 신고 창구는 찾을 수 있고, 조치의 범위를 알 수 있는가?
- 운영이 필요한 순간 응답이 있다는 근거가 있는가?
- 연합 제한으로 어느 연결이 영향을 받는가?
- 옮길 수 있는 관계·목록·기록은 각각 무엇이며 무엇을 수동으로 준비해야 하는가?
- 지금의 판단은 공개 기능 설명, 실제 운영 사례, 아니면 아직 시험하지 않은 가설인가?

세부 기원과 반례는 [질문 지도](/notes/knowledge-map/)와 연결된 concept·case Notes에 남겨 둔다.
